# 数据库基础补丁：先把直觉建立起来

> 这份补丁不追求术语完整，只做一件事：**让你先能在脑子里“看见”数据库在干什么**。

> 如果 Day 08–11 读得吃力，先读这份，再回去看源码和代码。

---

## 0. 一个贯穿全文的小例子

假设我们有一个很小的应用，保存用户余额：

```text
user:1 -> Alice, balance=100
user:2 -> Bob,   balance=50
```

我们只关心四件事：

1. 数据放在哪？（磁盘/内存）
2. 怎么快速找到某一行？（索引）
3. 改了数据，怎么保证断电不丢？（日志）
4. 两个人同时读写，怎么不互相踩？（并发控制）

数据库的复杂设计，基本都在回答这四个问题。

---

## 1. 页：数据库的“作业本一页”

磁盘不是按“一行数据”读写的，而是按**块**读写。数据库把磁盘空间切成固定大小的**页（page）**，例如 16 KiB。

你可以把数据库想成一本作业本：

```text
作业本
├── 第 1 页：user 表的一部分
├── 第 2 页：user 表的另一部分
├── 第 3 页：索引
└── ...
```

- 读一行数据，通常要把整页读到内存；
- 改一行数据，也是改内存里的这一页；
- 写回磁盘，也是整页写回。

**为什么要按页？**

- 磁盘/SSD 一次读写一个块更划算；
- 页是缓存、日志、恢复的基本单位；
- 一页里可以放很多行，减少 I/O 次数。

**一句话直觉：**

> 页 = 数据库从磁盘搬到内存的“最小箱子”。你改的不是一行，而是箱子里的某一行。

---

## 2. Buffer Pool：数据库的“书桌”

内存有限，不能把所有页都放进来。数据库划出一块内存做缓存，叫 **Buffer Pool**。

类比：

```text
书架（磁盘）  ->  书桌（Buffer Pool）  ->  你（SQL 执行器）
```

- 你要看第 5 页：先看桌上有没有；有就直接看（命中）；
- 没有就去书架拿（读磁盘），放到桌上（缓存）；
- 桌子满了，就要把一页放回书架（淘汰），腾出位置。

### 2.1 为什么需要 pin？

你正在看一本书，别人不能把它从桌上拿走。数据库用 **pin（固定）** 表示：

> 这一页正在被使用，不能淘汰。

用完要 `unpin`，别人才可以把它换出去。

### 2.2 什么是脏页？

你在书上用铅笔改了内容，但还没抄回书架上的原书。这一页就是**脏页**。

- 脏页不能直接丢掉，否则修改丢失；
- 淘汰脏页前，必须先把修改写回磁盘（flush）；
- 但“每改一次就写回”太慢，所以通常攒一批再写。

### 2.3 为什么 LRU 要分 young/old？

如果桌子只有 4 个位置，你突然要顺序翻 100 页（全表扫描），会把原来常用的 4 页全挤走。

数据库的对策：

- 新拿来的页先放在“冷区”（old）；
- 只有再次访问，才升级到“热区”（young）；
- 淘汰时先淘汰冷区。

这样一次扫描不会把热数据全部冲掉。

**一句话直觉：**

> Buffer Pool = 书桌；pin = 正在看的书不能收走；脏页 = 还没抄回原书的修改；young/old = 防止临时翻书把常用书挤走。

## 3. WAL：先写日记，再改作业本

假设你改作业本时突然断电，改了一半，怎么办？

数据库的做法：

```text
1. 先在“日记本”上写：我要把 user:1 的余额从 100 改成 80
2. 再把作业本上的 100 改成 80
```

这个“日记本”就是 **WAL（Write-Ahead Log，预写日志）**。

### 3.1 为什么先写日志？

因为日记本是**顺序追加**的，写起来快；作业本可能是随机页，改起来慢。

更重要的是：断电后可以看日记本：

- 哪些修改已经写了日志，但还没写回作业本？
- 重放这些日志，把作业本补到最新。

### 3.2 WAL 的规则

```text
日志必须先于对应的数据页落盘。
```

如果数据页先落盘、日志没落盘，崩溃后就没法恢复这个修改。

### 3.3 LSN：日记本上的“行号”

LSN（Log Sequence Number）可以理解成：

> **日记本上的行号/进度坐标。**

它不是时间，不是事务 ID，而是“这条日志在日志流里的位置”。

常用几个：

| 名字 | 直觉 |
|---|---|
| `current_lsn` | 日记本写到了哪一行 |
| `flushed_lsn` | 日记本真正被装订/寄走到哪一行（持久化） |
| `page_lsn` | 作业本这一页最后一次修改对应日记的哪一行 |
| `checkpoint_lsn` | 从日记本哪一行开始恢复 |
| `commit_lsn` | 这次提交写到了哪一行 |

### 3.4 group commit：一批人一起等快递

如果每个事务提交都 fsync 一次，太慢。数据库让多个事务一起等：

```text
T1 的提交在 LSN 100
T2 的提交在 LSN 110
T3 的提交在 LSN 120

一次 fsync 到 120
-> T1/T2/T3 都算持久化了
```

这就是 **group commit**：一次“快递”确认一批提交。

**一句话直觉：**

> WAL = 先写日记再改作业本；LSN = 日记行号；flush = 日记真的寄出去了；checkpoint = 从哪一行开始补作业。

## 4. 索引：B+ 树 vs LSM

现在回到“怎么快速找到 user:1”。

### 4.1 B+ 树：图书馆的卡片目录

B+ 树像图书馆：

```text
总目录 -> 分类目录 -> 书架 -> 某一页 -> 某一行
```

- 每层是一个有序的页；
- 页内记录有序，可以二分；
- 插入/删除可能触发页分裂/合并；
- 读路径短，范围查询方便；
- 但写入可能改多个页，随机写较多。

**适合：** 读多写少、范围查询、事务型业务。

### 4.2 LSM：收据堆 + 定期整理

LSM 像把每次修改写在一张新收据上：

```text
新修改 -> 先放桌上（MemTable）
桌上满了 -> 整理成一叠按日期排序的收据（SST）
收据越来越多 -> 定期合并（compaction）
```

- 写很快：追加 + 内存排序；
- 读可能要查很多叠收据；
- 合并会重写数据（写放大）；
- 删除用“作废标记”（tombstone），合并时才真正消失。

**适合：** 写多读少、日志/时序/大规模 KV。

**一句话直觉：**

> B+ 树 = 在卡片目录里改卡片；LSM = 不断写新收据，再定期合并。

## 5. MVCC：给每行贴“版本标签”

如果两个人同时读写：

```text
T1: 读 user:1
T2: 把 user:1 改成 80
T1: 再读 user:1，应该看到 100 还是 80？
```

数据库用 **MVCC（多版本并发控制）**：

- 每次修改产生一个新版本；
- 每个事务看到一个“快照”；
- 旧版本保留一段时间，供老事务读；
- 没人需要旧版本时，才能清理（purge/vacuum）。

你可以把一行想成：

```text
user:1, balance=100, version=10
user:1, balance=80,  version=12
```

- 老事务看 version 10；
- 新事务看 version 12；
- 清理线程删除没人需要的 10。

**一句话直觉：**

> MVCC = 不覆盖旧内容，而是保留多个版本，让不同事务各看各的快照。

## 6. 把这些串起来

一次写入：

```text
SQL 修改 user:1
  -> 先写 WAL（日记）
  -> 修改 Buffer Pool 里的页（作业本）
  -> 页变脏，等后台写回
  -> 提交时确保 WAL 持久化
```

一次读取：

```text
SQL 查 user:1
  -> 先查 Buffer Pool（桌上有没有）
  -> 没有就去磁盘读页（从书架拿）
  -> 在页内用索引/目录找记录
  -> 根据 MVCC 判断哪个版本可见
```

崩溃恢复：

```text
从 checkpoint_lsn 开始
  -> 重放 WAL
  -> 用 page_lsn 判断哪些修改已经应用
  -> 把未完成的事务回滚
```

---

## 7. 先记住这 7 句话

1. **页**是数据库从磁盘搬进内存的最小箱子。
2. **Buffer Pool** 是书桌；pin 表示正在用，脏页表示还没抄回原书。
3. **WAL** 是先写日记再改作业本。
4. **LSN** 是日记本上的行号/进度坐标。
5. **checkpoint** 是“从日记哪一行开始补作业”的书签。
6. **B+ 树** 是卡片目录；**LSM** 是收据堆加定期合并。
7. **MVCC** 是给每行保留多个版本，让不同事务看不同快照。
