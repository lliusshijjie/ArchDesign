# ArchDesign

> 用约 120 天，拆解主流中间件与基础设施中真正可迁移的设计。
>
> 目标不是“读完 60 次课”，而是留下 **48 张设计模式卡片 + 8 次复盘 + 4 个阶段工作坊**。

这个仓库是一套面向已有工程经验开发者的**隔日训练计划**。每两天推进一个单元，选一个真实系统的一个子模块，回答四个问题：

1. 它当年到底遇到了什么约束，才长成这个样子？
2. 它的数据流、状态机和关键路径是什么？
3. 哪几个实现技巧是“换了语言仍然成立”的？
4. 我自己的项目里，应该在什么边界内借鉴，什么时候不该借鉴？

## 1. 课程规模

- **周期**：60 次学习单元，**每两天一次，约 120 天**。
- **结构**：4 个阶段 ×（14 个核心单元 + 1 个阶段工作坊）= 60 次。
- **核心**：48 个主题深挖 + 8 次周复盘；另加 4 个阶段工作坊。
- **节奏**：每两天 **19:00（Asia/Shanghai）** 推进下一次；留出一天消化、补代码和读源码。
- **当前节奏**：Day 01–05 已完成；下一次 **2026-11-03 19:00** 从 Day 06 开始，之后每 48 小时一次（以会话里的定时任务为准）。
- **每次投入**：建议 90–120 分钟。
  - 45 分钟：读文章、画数据流；
  - 30 分钟：读指定源码/文档并做笔记；
  - 30 分钟：运行/修改代码，做一次破坏性实验；
  - 15 分钟：写一张模式卡片，更新进度。
- **最低完成线**（只有 45 分钟时）：读“背景 + 架构 + 技巧”，运行示例，回答自测题；代码练习留到下一个单元前。
- **不绑定日历日期**：按“单元”推进，断档后从下一个未完成单元继续，不需要补日期。

### 1.1 技术栈与取材偏好

根据你的背景（**C++ > Rust > Java**），后续课程按下面的原则取材：

- **代码默认 C++20**；Rust 作为第二实现/特定主题对照；不强制每课双语言。
- **Java 只在它是事实标准或最佳教学样本时出现**：`ThreadPoolExecutor`、Netty、Kafka、Log4j2 等；重点追机制，不要求通读整个仓库。
- **每个主题尽量给 C++/Rust 生态的对应物**；如果 C++/Rust 有更贴近生产、更适合你复用的实现，优先用它作为主线。
- **不以语言偏好牺牲案例质量**：Java 官方实现仍然是重要参考，但会明确标注“这是 Java 参考实现，练习用 C++/Rust 重写”。
- 代码示例默认跨平台；涉及 `epoll`、`io_uring`、`fork` 等 Linux 特性时会明确标注。

| 主题 | 主案例（可能是 Java/C/Go） | C++/Rust 对照 |
|---|---|---|
| 线程池/执行器 | OpenJDK `ThreadPoolExecutor` | Folly Executor、Boost.Asio、Taskflow、Rust Rayon |
| 事件循环 | Redis `ae`、Netty | Seastar、Boost.Asio、libuv（C）、Rust mio/Tokio |
| 定时器 | Netty `HashedWheelTimer`、Kafka `TimingWheel` | C++ 时间轮实现、Rust `tokio::time` |
| 异步日志 | Log4j2 `AsyncLogger` | spdlog、quill、Rust `tracing` |
| 存储引擎 | InnoDB（C/C++）、PostgreSQL（C）、LevelDB/RocksDB（C++） | RocksDB、Redb、Rust `sled` 等 |
| 消息队列 | Kafka、RocketMQ、Pulsar | Redpanda（C++）、Aeron（C++/Java）、librdkafka、NATS（Go） |
| 共识/协调 | etcd（Go）、ZooKeeper（Java） | braft、NuRaft、raft-rs、etcd |
| 运行时调度 | Go GMP、Tokio | Tokio、Seastar、Folly、Rust async runtime |

> 结论：**主线用 C++/Rust 的机制和代码，Java 作为“官方实现/最佳样本”对照**。这样既贴近你的技术栈，也不丢掉 Java 生态里最值得学的设计。

### 四个阶段与工作坊

60 次课不是把 56 个核心单元简单拉长，而是在每 14 个核心单元后加一个**阶段工作坊**，用来压测、复盘和迁移：

| 阶段 | 核心单元 | 阶段工作坊 | 重点 |
|---|---|---|---|
| 1 | Day 01–14 | **工作坊 A**：存储引擎压测与崩溃恢复 | 给 Mini KV 注入断电/部分写，测恢复时间与写放大 |
| 2 | Day 15–28 | **工作坊 B**：消息系统故障注入 | 重复、乱序、积压、消费者崩溃，验证 Outbox 与幂等 |
| 3 | Day 29–42 | **工作坊 C**：调度与锁的混沌实验 | 时钟偏移、网络分区、lease 过期，验证 fencing |
| 4 | Day 43–56 | **工作坊 D**：个人项目迁移工作坊 | 选 3 个模式做 PoC、设计评审、30 天落地计划 |

顺序是：`Day 01–14 → 工作坊 A → Day 15–28 → 工作坊 B → Day 29–42 → 工作坊 C → Day 43–56 → 工作坊 D`。

4 ×（14 + 1）= **60 次**；每两天一次，约 **120 天**。

完整逐次清单见 **[ROADMAP.md](ROADMAP.md)**。

### 为什么这样排序

- **先单机，后分布式**：线程池、事件循环、存储引擎是后面所有中间件的底座。没理解 WAL 和 LSM，就很难真正理解 Kafka 的持久化与 Redis 的 AOF。
- **先机制，后策略**：W1–W2 讲“怎么工作”，W3–W6 讲“在复制、分片、共识、调度下如何取舍”，W7–W8 讲“如何观测、关闭、测试和落地”。
- **每个阶段一次组合**：每 14 个核心单元后停下来，把本周/本阶段的机制拼成一个能跑、能坏、能恢复的小系统。孤立地记知识点没有用，能组合才有用。
- **隔日节奏**：每次 90–120 分钟，中间留一天消化。深度学习需要“间隔”，不是把一天塞满。

## 3. 每次闭环

每篇课文都按同一节奏组织：

```text
问题与结论
  → 设计背景（约束、失败案例）
  → 架构与数据流（图）
  → 源码关键路径（方法名/状态机）
  → 3–6 个可迁移技巧
  → 反例与边界
  → C++/Rust 最小实现
  → 复用清单 + 练习 + 自测
```

建议每次按这个顺序使用：

1. **先不看代码**，读“背景”和“架构”，自己在纸上画一遍数据流。
2. 读“源码关键路径”，把方法名和状态迁移记下来；不要逐行读整个文件。
3. 编译并运行本次代码，先跑通，再做一次“破坏性实验”（改容量、改超时、注入异常、杀进程）。
4. 把文章最后的“模式卡片”用自己的话重写一遍，贴到自己的笔记里。
5. 在 `ROADMAP.md` 勾选本次进度，写一句“我这次真正学到的”。

> 学习效果不取决于读了多少，而取决于你是否能**预测**系统在边界条件下的行为。

## 7. 每次交付标准

一篇合格的课文必须包含：

- [ ] 设计背景：至少一个真实约束或失败模式，而不是“因为它很流行”。
- [ ] 架构图：数据流/状态机/时序，至少一张。
- [ ] 源码坐标：具体到文件、类、方法或协议字段。
- [ ] 关键技巧：3–6 条，并说明代价和适用边界。
- [ ] 可运行代码：C++20 或 Rust；不能运行时必须明确标注伪代码/平台限制。
- [ ] 反例：至少一个“看起来对但会出事”的用法。
- [ ] 复用清单：接口、测试、监控三个维度各至少一条。
- [ ] 自测题：能从文章中找到依据，但不需要背诵。

## 8. 代码环境

- 主要语言：**C++20**；第二语言：**Rust**；**Java 仅用于官方源码/概念参考**，不作为练习实现语言。
- 构建：CMake ≥ 3.20 + 任意 C++20 编译器（GCC 11+/Clang 14+/MSVC 19.30+）。
- 平台：示例优先跨平台；涉及 `epoll`、`io_uring`、`fork` 等 Linux 特性时会明确标注“仅 Linux”。
- 并发示例默认链接线程库；Windows 下使用 MinGW/GCC 或 MSVC 均可。
- 代码追求“**最小可运行、可修改、可测试**”，不追求生产级完整度；生产化缺口会在文中列出。

## 9. 三条学习原则

1. **先问约束，再看方案。** 同一个“单线程”在 Redis 是优势，在数据库写入路径可能是瓶颈；脱离约束记结论没有意义。
2. **区分机制与策略。** 线程池的“队列 + 工作线程”是机制，“队列多长、满了怎么办”是策略。可复用的一般是机制和取舍方法，不是参数。
3. **每学一个设计，至少找一个反例。** 能说清“什么时候不该用”，才算真正掌握。
